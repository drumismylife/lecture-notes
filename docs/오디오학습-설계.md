## 1. 비판 → 수정 이력 (추적용)

### 1회차 비판 — 기술적 타당성 중심

**축1에 대해**
- **C1-1** 세그먼트 원장의 실제 작업량이 과소평가됐다. 실측 녹취 파일은 30~86 KB(`헬라어2_9강.txt` 85,808 bytes)다. 이걸 화제전환 단위로 쪼개면 30~60 세그먼트가 나오고, 4열 표를 전부 채우면 노트 1편당 상당한 추가 출력이 생긴다. **5과목 × 매주**면 지속 가능하지 않다.
- **C1-2** "세그먼트 커버리지 X/X(100%)"라는 **자체보고 수치는 검증 불가능하다.** 검증할 수 없는 숫자를 노트에 적게 하는 것은, 축1이 막으려던 바로 그 문제(안 한 걸 한 것처럼 매끄럽게 서술)를 검증 요약 안에 다시 만들어 넣는 것이다. 4출처 건수(자료근거 N·교수강조 N…)도 마찬가지로 아무도 대조할 수 없는 숫자다.
- **C1-3** 배지가 정보를 잃는 구간이 있다. `min`(PPT 의존도 낮음)·`phil`(낮음) profile은 스스로 "강의추가가 다른 과목보다 많이 나오는 게 정상"이라고 적어 뒀다. 그러면 문단 대부분에 📌가 붙고 **배지가 배경색이 된다.**
- **C1-4** ASR 불확실 인라인 표시가 많아지면 노트 가독성이 떨어지고, 특히 **그 노트를 그대로 낭독·오디오화하면 소음이 된다**(축2와 직접 충돌).
- **C1-5** (0-2) 규약을 넣은 5개 profile은 **이미 끝난 학기 과목**이다. 지금 상태로는 2학기 신규 과목에 아무것도 상속되지 않는다.

**축2에 대해**
- **C2-1** (0-6) `nlm` 인터페이스를 잘못 가정했다. 비동기 생성인데 `deploy.py` 안에 넣으면 배포가 수 분~십수 분 멈추거나, 안 멈추면 파일이 아직 없다.
- **C2-2** (0-5) **오디오를 git에 커밋한다는 계획이 가장 큰 결함.** git 히스토리는 줄어들지 않는다. 5과목 × 15주 × 15~25 MB ≈ 학기당 1~2 GB가 영구히 쌓인다. `.git`이 이미 335 MB인데 여기서 GitHub 권장 한도(1 GB)를 학기 하나로 넘긴다. 클론·푸시가 느려지고 되돌릴 수 없다.
- **C2-3** (0-1) `notebook_id`가 0개다. "1단계(기존)"라고 적힌 것이 사실은 **한 번도 동작한 적 없는 코드**다. 즉 축2는 1단계부터 신규 구축이다.
- **C2-4** (0-3) 5단계 "data.js narration 등록"에 해당하는 코드가 없다.
- **C2-5** **배달 경로를 검토하지 않고 사이트 플레이어로 확정해 버렸다.** NotebookLM 모바일 앱 자체 재생, 팟캐스트 앱, 파일 앱 등 더 싼 경로를 비교하지 않았다. 사이트 플레이어를 전제했기 때문에 Media Session 개선이 과제로 따라 나온 것이다 — 순서가 거꾸로다.
- **C2-6** **축1과 축2가 철학적으로 충돌한다.** 축1은 "환각 0, 매끄럽게 고쳐 쓰지 않기"에 큰 비용을 썼다. 축2의 deep_dive는 진행자 2명이 자료를 **자유롭게 재구성해 이야기하는** 형식이다. 오디오에서 들은 표현을 사실로 받아들이면 축1 투자가 무효화된다.
- **C2-7** "원본 녹취 + PPT도 소스로 추가"는 ① (0-8) 저작권·개인정보 정책과 충돌하고 ② 노트북당 소스 개수를 3배로 먹는다(주 3소스 × 15주 = 45 — 무료 티어 한도에 근접).
- **C2-8** 결론부(설명형=NotebookLM / 토론=Claude 음성)가 **미검증 가정 위에 세워져 있다.** Claude 음성모드는 오너가 써 본 적이 없고, 음성 세션 중 web fetch 도구가 호출되는지도 모른다. 검증 없이 이걸 "결론"으로 부르면 안 된다.

### 2회차 비판 — 우선순위·구현 순서·사용자 마찰 중심

- **D-1 자동화 ROI가 안 맞는다.** 1차 수정안도 여전히 "파이프라인"을 짓는다. 그런데 실제 작업량은 주 1회 과목당 명령 2~3줄이다. 학기 전체로 봐도 75회 × 3분 ≈ 4시간. 반면 비공식 CLI에 의존하는 스크립트는 **작성 + API 변경 시 유지보수**가 그보다 비싸질 수 있다. → **완전 자동화가 아니라 "얇은 헬퍼 + 손 실행"이 정답.**
- **D-2 검증 시점이 잘못됐다.** 오늘은 8월 4일, 2학기 과목은 미정이다. "다음 주차 노트가 나오면 시험해 본다"는 계획은 **개강 첫 주에 디버깅을 하게 만든다.** 이미 배포된 노트(예: `output/2026-summer/greek2/week10.html`)로 **지금 전 구간을 검증할 수 있다.** 신규 노트를 기다릴 이유가 전혀 없다.
- **D-3 검증 순서가 비용 대비 정보량 순이 아니다.** 가장 싸면서 설계를 가장 크게 뒤집을 수 있는 검증을 먼저 해야 한다. **"NotebookLM 한국어 오디오 개요가 실제로 쓸 만한가"** — 이게 아니면 축2 전체가 무의미한데, 확인 비용은 10분이다.
- **D-4 운전 중 마찰에서 진짜 결격사유는 Media Session이 아니다.** ① **오프라인 재생**(터널·지하·데이터) ② **재생위치 기억(이어듣기)** — 20~30분 트랙을 브라우저에서 듣다가 화면을 끄거나 앱을 전환하면 위치를 잃는다. 사이트 플레이어는 이 둘을 구조적으로 못 준다(0-4). **즉 사이트 플레이어는 운전용으로 애초에 부적합하며, Media Session만 붙여도 해결되지 않는다.** 이건 강등이 아니라 **탈락** 사유다.
- **D-5 청취량 과잉.** 5과목 전부 자동 생성하면 주당 20분 × 5 = 100분이 쌓인다. 실제 운전 시간을 초과하면 미청취분이 적체되고 시스템 전체를 안 쓰게 된다. SKILL.md는 이미 낭독 mp3를 **"명시적 요청 시에만"**으로 규정해 뒀다(208-212행) — **이 원칙을 오디오 개요에도 그대로 적용**하는 게 일관적이다.
- **D-6 `--focus` 문구 5개를 미리 쓰는 것은 오버엔지니어링.** `--focus`가 한국어로 실제 반영되는지도 모르는 상태에서 과목별 지침을 5개 작성하는 건, 검증 전 확산이다. 1개 과목에서 focus 유/무를 비교한 뒤 확산해야 한다.
- **D-7 축1 커밋 대기의 부작용.** profile 5개는 "2학기 확정 시 커밋"으로 묶여 있는데, 그 사이 실효를 가진 것은 SKILL.md뿐이다. 그런데 SKILL.md는 이미 규약을 담고 있으므로, **profile 5개의 수정은 사실상 문서적 가치만 있다.** 미래 과목에 실효를 주는 유일한 조치는 **profile 템플릿화**다(C1-5의 결론을 강화).
- **D-8 안전.** 운전 중 화면 조작은 전제에서 배제해야 한다. "출발 전 세팅 완료, 주행 중엔 오디오 컨트롤만" 원칙을 설계에 명시.

## (a) 목표

완성된 주차 노트를 기반으로,

1. **설명형 청취** — 운전 중 이어폰/차량 스피커로 "이해되게 풀어 주는" 한국어 음성을 듣는다.
2. **실시간 토론** — 그 내용을 두고 한국어 음성으로 되묻고 답을 듣는다.

**정본은 언제나 노트 HTML이다.** 오디오·토론은 이해와 복습을 위한 보조 매체이며,

## (c) 축2 (오디오 학습) — 최종 설계

### 설계 원칙 (2회 비판을 통과한 것만)

1. **검증이 먼저, 구축은 나중.** 각 단계는 이전 단계의 검증 통과를 게이트로 갖는다.
2. **가장 싼 경로부터.** 앱으로 되는 일에 파이프라인을 짓지 않는다.
3. **오디오 파일을 git에 커밋하지 않는다.** (`.git` 335 MB, 이미 91 MB의 m4a가 들어가 있음)
4. **온디맨드.** 요청한 과목·주차만 생성한다. 전 과목 자동 생성 없음.
5. **정본은 노트.** 오디오 내용의 노트 역수입 금지.
6. **출발 전 세팅 완료.** 주행 중에는 재생/일시정지 외 조작을 전제하지 않는다.
7. **실패해도 배포는 성공.** 오디오 관련 실패가 노트 배포를 막지 않는다(기존 패턴 유지).

**파이프라인에 넣지 않는다.** deploy.py가 모바일 앱을 조작할 방법이 없고(브리핑 7번), 그럴 필요도 없다.

**출발 전 세팅 절차** (D-8)
1. 아이폰 Claude 앱에서 새 대화를 연다.
2. 노트 직접 링크를 붙여넣고 "이 노트 읽고, 이 내용으로 대화할 준비를 해 줘"라고 텍스트로 보낸다.
   예: `https://drumismylife.github.io/lecture-notes/output/2026-summer/greek2/week10.html`
   - **사이트 홈(index.html) 링크는 쓰지 않는다** — data.js를 JS로 읽는 SPA라 fetch가 빈 껍데기를 본다.
   - **개별 주차 노트는 `<script>` 0개의 완전 정적 문서임이 확인됐다**(0-7).
3. 노트를 읽었다는 응답을 확인한 뒤 **음성 모드로 전환**하고 출발한다.
4. `deploy.py`가 배포 후 노트 URL을 클립보드에 넣어 주면(`pbcopy`) 1번의 마찰이 줄어든다 —
   **선택적 개선, 3줄짜리**. 이건 넣어도 좋다.

## (e) 리스크 / 한계

**R-1 저장소 팽창 (되돌릴 수 없음 · 최고 위험)**
`.git`이 이미 335 MiB이고 `output/`에 50 MB·41 MB짜리 m4a가 커밋돼 있다.
오디오를 매주 커밋하면 학기당 1~2 GB가 **영구히** 쌓인다(git 히스토리는 줄지 않는다).
→ **대응: 오디오 파일을 저장소에 넣지 않는다.** `.gitignore`에 `*.m4a` 추가를 검토.
(기존 91 MB의 m4a 2개를 히스토리에서 제거하는 것은 별건이며, 리라이트 비용이 커서 권하지 않는다.)

**R-2 축1과 축2의 사실성 충돌**
deep_dive는 진행자 2명이 자료를 자유롭게 재구성해 이야기하는 형식이다. 축1이 비싸게 확보한
"환각 0, ASR 불확실은 불확실로"가 오디오에서 매끄러운 단정으로 되돌아올 수 있다.
→ **대응: 노트가 정본. 오디오에서 들은 내용을 노트에 반영하지 않는다.** 시험 대비 사실 확인은
항상 노트·교재 캡처로 되돌아간다.

**R-3 저작권·개인정보의 클라우드 이동**
`.gitignore`는 녹취·자막·교재 캡처·카톡 백업을 저작권·개인정보 사유로 저장소에서 배제하고 있다(0-8).
"원본 녹취·PPT도 소스로 추가" 안은 **같은 자료를 구글 서버로 보내는 별개 판단**이다.
→ **대응: 1차 설계에서는 노트 URL 1개만 소스로 쓴다.** 오디오 품질이 부족하다고 **판정된 뒤에만**,
① 카톡 백업은 절대 제외 ② 교재 캡처(출판사 저작물)는 제외 ③ 본인 작성물·본인 강의 녹취만 검토 —
이 3개 체크리스트를 통과한 자료에 한해 추가한다.

**R-4 비공식 CLI 의존**
`nlm`은 NotebookLM의 비공식 CLI다. 구글이 내부 API를 바꾸면 파이프라인이 조용히 깨진다.
→ **대응: 오디오 관련 실패는 항상 경고만 내고 노트 배포는 성공시킨다**(기존 `deploy.py` 패턴 유지).
자동 트리거를 만들지 않는 것 자체가 방어책이다(D-1).

**R-5 무료 티어 한도**
오디오 개요 하루 3개. 온디맨드 생성이면 실질 제약은 낮지만, 시험 전 몰아서 만들 때 걸린다.
→ **대응: 시험 대비용 오디오는 며칠에 나눠 생성.** 한도 초과가 잦아지면 그때 Plus를 검토.

**R-6 청취 적체**
주당 100분의 오디오가 쌓이면 시스템 자체를 안 쓰게 된다.
→ **대응: 온디맨드.** "이번 주 이 과목이 어려웠다" 싶을 때만 만든다.

**R-7 안전**
운전 중 화면 조작은 설계 전제에서 배제한다. 출발 전 세팅을 완료하고, 주행 중에는 재생/일시정지와
음성 대화만 한다.

**R-8 언어 한계 (해결 불가, 관찰만)**
NotebookLM Interactive Mode(AI 진행자와의 실시간 토론)는 현재 영어 전용이며 유료도 이를 풀지 않는다.
한국어가 열리면 **축2의 청취와 토론이 하나의 도구로 합쳐지므로**, 이 설계는 그때 크게 단순해진다.
주기적으로(학기마다) 확인할 가치가 있다.
